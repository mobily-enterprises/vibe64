# Connected development: Rust Cargo (`cargo`)

This fixture proves that a Cargo package can build against an unpublished
change in a connected library checkout, using Cargo's own override mechanism,
without editing its tracked `Cargo.toml` or `Cargo.lock`.

## The recipe

1. The consumer (`app/`) depends on the library by its ordinary crate name and
   version: `connected-library = "1.0.0"` from crates.io. Its tracked
   `Cargo.lock` records the registry source and checksum.
2. Vibe64 writes the sources map to `.development/connected.json`.
3. **Prepare** (`sh tooling/connected.sh prepare .development/connected.json`)
   works as follows:
   - The wrapper compiles `tooling/connected.rs` with `rustc` into
     `.development/tooling/`. The tool uses only the standard library, so it
     needs no Cargo project and never touches a lockfile.
   - The tool reads the map with a small JSON reader, because std has none.
     For each `cargo` entry, it reads `[package] name`/`version` from
     `sourceRoot/Cargo.toml`.
   - It runs `cargo metadata --no-deps` to find where the consumer declares
     that dependency. The dependency's source chooses the patch table:
     crates.io means `[patch.crates-io]`, and a git URL means
     `[patch."<url>"]`.
   - It writes an untracked `.cargo/config.toml`:

     ```toml
     # Generated by tooling/connected.sh prepare. Untracked; do not commit.
     [resolver]
     lockfile-path = "/abs/app/.development/cargo/Cargo.lock"

     [patch.crates-io]
     "connected-library" = { path = "/abs/path/to/library/checkout" }
     ```

   - On every run, it seeds `.development/cargo/Cargo.lock` with a copy of the
     tracked `Cargo.lock`. It then runs `cargo metadata` so that Cargo applies
     the patch to that derived lock. The derived lock differs from the tracked
     lock only in the patched entries. Running Prepare again gives identical
     results.
   - It refuses to replace a `.cargo/config.toml` that it did not generate. If
     no `cargo` repository is connected, it removes both generated files.
4. **Verify** (`sh tooling/connected.sh verify .development/connected.json`)
   proves that the patch is in effect:
   - It runs `cargo metadata --locked`. The connected crate must resolve with
     `source: null` and `manifest_path` = `sourceRoot/Cargo.toml`. It must be
     the only package with that name in the graph, and the consumer's root
     package must depend on it.
   - The derived lock must exist, which shows that `resolver.lockfile-path` is
     in effect.
   - It runs `cargo build --locked` and checks that the bytes of `Cargo.toml`
     and `Cargo.lock` are unchanged.
5. After Prepare, ordinary `cargo build`, `cargo run` and `cargo test` commands
   run from inside the consumer use the connected checkout. Cargo reads
   `.cargo/config.toml` from the current directory and its parent directories.
   It also rebuilds when files in the connected checkout change, because the
   patch is a `path` source; the proof checks this.

`.gitignore` excludes `/target/`, `/.development/` and `/.cargo/config.toml`.

## Cargo.lock: the important detail

When a `[patch]` applies, Cargo rewrites the lockfile. The patched package
loses its `source` and `checksum`:

```
 [[package]]
 name = "connected-library"
 version = "1.0.0"
-source = "registry+https://github.com/rust-lang/crates.io-index"
-checksum = "84bc…200c"
```

If `[patch]` were the only change, the tracked `Cargo.lock` would be modified.
`--locked` would also refuse to build, because the lock needs updating.

This recipe uses **`resolver.lockfile-path`** (environment variable
`CARGO_RESOLVER_LOCKFILE_PATH`). It became stable in **Cargo 1.97**. The Cargo
configuration reference says: "Specifies the path to the lockfile to use when
resolving dependencies. This option is useful when working with read-only
source directories. The path must end with `Cargo.lock`." Cargo reads and writes
only the derived lock, so the tracked `Cargo.lock` is never opened for writing.
Because the derived lock starts from the tracked one, versions of the other
dependencies stay pinned exactly as committed.

Rejected alternatives:

- Restoring the lock after each build is racy and loses edits.
- `git update-index --skip-worktree` hides changes instead of preventing them.
- Source replacement with a fake checksum is not acceptable. Cargo treats
  registry/directory sources as immutable, so edits would not rebuild, and
  the checksum would have to be falsified.
- `--config` on every command works with the same keys, but every command the
  developer or agent types would have to carry it.

With a Cargo older than 1.97, there is no supported way to apply a `[patch]`
without rewriting the workspace's `Cargo.lock`. Requiring 1.97+ is the safe
choice.

## Running the proof

```
PATH=$CARGO_HOME/bin:$PATH RUSTUP_HOME=… CARGO_HOME=… TMPDIR=/some/scratch bash prove.sh
```

Requirements:

- `cargo`/`rustc` 1.97 or newer, `git`, `tar`, `sha256sum` and a C linker
  (`cc`) on `PATH`.
- With rustup, `RUSTUP_HOME` (and `CARGO_HOME`) for the toolchain.
- Tested with cargo 1.99.1 (5f94df478 2026-08-27), rustc 1.99.1
  (58cf8f9c3 2026-10-13), git 2.43.0 and Linux x86_64.
- The toolchain was installed into scratch with
  `sh rustup-init.sh --no-modify-path -y --profile minimal`, with `RUSTUP_HOME`
  and `CARGO_HOME` set to the scratch directory.
- No network is needed. The script sets `CARGO_NET_OFFLINE=true`.

What `prove.sh` does:

1. It "publishes" `library/` with `cargo package` into a local directory source
   (an extracted `.crate` plus `.cargo-checksum.json`). The file
   `$WORK/.cargo/config.toml` replaces crates.io with that source. It sits
   outside the consumer checkout, like a user-level mirror configuration.
2. It copies `app/` and runs `cargo generate-lockfile`, which records
   crates.io and the checksum. It checks that the app prints
   `library 1.0.0 published`, then runs `git init` and commits the app.
3. It removes the published crate and checks that a build now fails, so the
   published crate cannot quietly supply the dependency.
4. It copies the library and changes its marker. This change is unpublished.
   It writes the sources map, runs Prepare twice (the config and derived lock
   must be identical) and runs Verify. It checks that `cargo run --locked`
   prints the modified marker.
5. It changes the checkout again and checks that the new output appears without
   another Prepare.
6. It checks that the checkout is clean and that `Cargo.toml` and `Cargo.lock`
   are unchanged.
7. Negative checks: Verify must fail when `.cargo/config.toml` is missing, and
   when the connected crate's version (2.0.0) no longer meets the requirement,
   which leaves the patch unused.

## Limitations

- **Precedence:** a `--config` on the command line, `CARGO_RESOLVER_LOCKFILE_PATH`
  or `CARGO_TARGET_DIR` in the environment overrides `.cargo/config.toml`.
  `CARGO_TARGET_DIR` is harmless. If a project tracks its own
  `.cargo/config.toml`, Prepare refuses to replace it. That project would need
  another config location in the directory chain, or explicit `--config`.
- **Version match:** the connected crate's version must still satisfy the
  consumer's requirement. Otherwise Cargo ignores the patch and warns. Verify
  catches this.
- **Supported sources:** only crates.io and git dependencies are handled.
  Alternative registries are rejected by this script, although Cargo supports
  `[patch.<registry-name>]`. A virtual-workspace `sourceRoot` (with no
  `[package]`) is not supported.
- **New dependencies:** if the connected checkout adds dependencies, Prepare may
  need the network, or a filled registry cache, to resolve them.
- **Tooling compilation:** `tooling/connected.rs` is compiled with plain `rustc`
  on the first run, which takes about a second. It is rebuilt when the source
  is newer than the binary.

## `composition` relationship

Cargo has a single native mechanism for local-source override. Both
`dependency` and `composition` entries are therefore wired the same way, by a
`[patch]` path. The relationship is recorded in the generated config comment
and the output. Any further meaning of `composition` is handled at the
Genesis/Vibe64 level, outside Cargo. Verify still requires the consumer to
depend on every connected crate.
