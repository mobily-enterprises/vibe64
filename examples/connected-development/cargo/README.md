# Connected development: Rust Cargo (`cargo`)

This fixture proves Vibe64's own `cargo` treatment: a Cargo package builds
against an unpublished change in a connected library checkout, using Cargo's
own override mechanism, without editing its tracked `Cargo.toml` or
`Cargo.lock`; and Save moves the tracked lock only once the checkout's version
is published.

## Vibe64's Cargo treatment

`packages/vibe64-project/src/server/connectedAdapters/cargo.js`. The consumer
(`app/`) depends on the library by its ordinary crate name and version,
`connected-library = "1.0.0"` from crates.io; its tracked `Cargo.lock` records
the registry source and checksum. `app/genesis/stack.md` declares only
``- Default package type: `cargo` ``: Vibe64 itself puts the connection in
effect, and the project writes no Prepare or Verify command. `prove.sh` calls
`../vibe64-adapter.mjs` (the adapter steps workspace preparation runs) and
`../vibe64-adapter.mjs bump` (what Save asks of the adapter).

**Apply** (after the project's Prepare steps):

- Reads `[package] name`/`version` from each connected `sourceRoot/Cargo.toml`.
- Refuses a `.cargo/config.toml` it did not write, a tracked
  `.cargo/config.toml` or `.development/cargo/Cargo.lock`, and a Cargo older
  than 1.97 (`cargo --version`).
- Runs `cargo metadata --no-deps` to find where the session's packages declare
  each crate: crates.io means `[patch.crates-io]`, a git URL `[patch."<url>"]`.
- Writes, through Vibe64's derived-files helper and its own Git exclude block:

  ```toml
  # Generated by Vibe64 for connected development. Untracked; do not commit.

  [resolver]
  lockfile-path = "/abs/app/.development/cargo/Cargo.lock"

  [patch.crates-io]
  "connected-library" = { path = "/abs/path/to/library/checkout" }
  ```

  and seeds `.development/cargo/Cargo.lock` with the tracked `Cargo.lock`, then
  runs `cargo metadata` so Cargo applies the patch to that derived lock. If
  Cargo wrote the tracked `Cargo.lock` instead, it puts it back and refuses.
- After it, ordinary `cargo build`, `cargo run` and `cargo test` commands run
  in the session source use the checkout, and rebuild when it changes (a
  `path` source): no watcher.

**Proof** (after the project's Verify steps): the config is Vibe64's and
patches the crate to this session's copy, and the derived lock holds the crate
from the checkout (session status stops there, from files alone). In
preparation Cargo answers instead: `cargo metadata --locked` must resolve the
crate with `source: null` from `sourceRoot/Cargo.toml`, as the only package of
that name, a dependency of a session package, with the tracked `Cargo.lock`
unchanged. The reason names the version and requirement when Cargo ignored the
patch. (The proof does not build: the app's own build pays that.)

**Save** (`locked` and `bump`): `locked` reads the checkout's version beside the
tracked `Cargo.lock`'s registry entry, which Staging and Production build.
`bump` runs `cargo update --manifest-path <app>/Cargo.toml --package
<crate>@<locked> --precise <checkout version>` from the connected copy: Cargo
reads configuration from its working directory, so the session's patch is not
read and the tracked `Cargo.lock` takes the published crate, checksum
included. When the version falls outside `Cargo.toml`'s requirement, the
requirement moves to it first. An unpublished version changes nothing (both
files go back as they were); an unreachable registry changes nothing and says
so. Apply then runs again, so the session keeps building the checkout.

**Restore**: once no Cargo connection remains, preparation removes Vibe64's
config and derived lock (never a config it did not write).

`.gitignore` excludes `/target/`, `/.development/` and `/.cargo/config.toml`;
Vibe64's exclude block covers a project whose `.gitignore` does not.

## Cargo.lock: the important detail

When a `[patch]` applies, Cargo rewrites the lockfile. The patched package
loses its `source` and `checksum`:

```
 [[package]]
 name = "connected-library"
 version = "1.0.0"
-source = "registry+https://github.com/rust-lang/crates.io-index"
-checksum = "84bc…200c"
```

If `[patch]` were the only change, the tracked `Cargo.lock` would be modified.
`--locked` would also refuse to build, because the lock needs updating.

This recipe uses **`resolver.lockfile-path`** (environment variable
`CARGO_RESOLVER_LOCKFILE_PATH`). It became stable in **Cargo 1.97**. The Cargo
configuration reference says: "Specifies the path to the lockfile to use when
resolving dependencies. This option is useful when working with read-only
source directories. The path must end with `Cargo.lock`." Cargo reads and writes
only the derived lock, so the tracked `Cargo.lock` is never opened for writing.
Because the derived lock starts from the tracked one, versions of the other
dependencies stay pinned exactly as committed.

Rejected alternatives:

- Restoring the lock after each build is racy and loses edits.
- `git update-index --skip-worktree` hides changes instead of preventing them.
- Source replacement with a fake checksum is not acceptable. Cargo treats
  registry/directory sources as immutable, so edits would not rebuild, and
  the checksum would have to be falsified.
- `--config` on every command works with the same keys, but every command the
  developer or agent types would have to carry it.

With a Cargo older than 1.97, there is no supported way to apply a `[patch]`
without rewriting the workspace's `Cargo.lock`. Requiring 1.97+ is the safe
choice.

## Running the proof

```
PATH=$CARGO_HOME/bin:$PATH RUSTUP_HOME=… CARGO_HOME=… TMPDIR=/some/scratch bash prove.sh
```

Requirements:

- `cargo`/`rustc` 1.97 or newer, `git`, `tar`, `sha256sum` and a C linker
  (`cc`) on `PATH`.
- With rustup, `RUSTUP_HOME` (and `CARGO_HOME`) for the toolchain.
- Tested on usone with cargo 1.99.0 (5f94df478 2026-08-27), rustc 1.99.1
  (58cf8f9c3 2026-10-13) from nixpkgs (`nix shell nixpkgs#cargo nixpkgs#rustc
  nixpkgs#gcc`), git 2.53.0, Node v26.5.0 and Linux x86_64; the proof took
  3.8 s (run `cad-pyrust-3`, 2026-11-23).
- No network is needed. The script sets `CARGO_NET_OFFLINE=true`.

What `prove.sh` does:

1. It "publishes" `library/` with `cargo package` into a local directory source
   (an extracted `.crate` plus `.cargo-checksum.json`). The file
   `$WORK/.cargo/config.toml` replaces crates.io with that source. It sits
   outside the consumer checkout, like a user-level mirror configuration.
2. It copies `app/` and runs `cargo generate-lockfile`, which records
   crates.io and the checksum. It checks that the app prints
   `library 1.0.0 published`, then runs `git init` and commits the app.
3. It removes the published crate and checks that a build now fails, so the
   published crate cannot quietly supply the dependency.
4. It copies the library and changes its marker. This change is unpublished.
   It writes the sources map, runs apply twice (the config and derived lock
   must be identical) and the proof. It checks that `cargo run --locked`
   prints the modified marker.
5. It changes the checkout again and checks that the new output appears without
   another apply.
6. It checks that the checkout is clean and that `Cargo.toml` and `Cargo.lock`
   are unchanged.
7. Save: it moves the checkout to 1.1.0 (the session keeps building it), runs
   `bump` before 1.1.0 is published (nothing moves), publishes 1.1.0 to the
   stand-in registry, runs `bump` again and checks that the tracked
   `Cargo.lock` now takes 1.1.0 from the registry, `Cargo.toml` is unchanged
   (`^1.0.0` admits it), the proof still passes and the app still prints the
   checkout's marker. It commits that, as Save would.
8. Negative checks: the proof must fail when `.cargo/config.toml` is missing,
   and when the connected crate's version (2.0.0) no longer meets the
   requirement, which leaves the patch unused.

## Limitations

- **Precedence:** a `--config` on the command line, `CARGO_RESOLVER_LOCKFILE_PATH`
  or `CARGO_TARGET_DIR` in the environment overrides `.cargo/config.toml`.
  `CARGO_TARGET_DIR` is harmless. If a project tracks its own
  `.cargo/config.toml`, Vibe64 refuses to replace it. That project would need
  another config location in the directory chain, or explicit `--config`.
- **Version match:** the connected crate's version must still satisfy the
  consumer's requirement. Otherwise Cargo ignores the patch and warns. The proof
  catches this and says which version and requirement.
- **Supported sources:** only crates.io and git dependencies are handled.
  Alternative registries are rejected by the adapter, although Cargo supports
  `[patch.<registry-name>]`. A virtual-workspace `sourceRoot` (with no
  `[package]`) is not supported.
- **New dependencies:** if the connected checkout adds dependencies, apply may
  need the network, or a filled registry cache, to resolve them.
- **Renamed or table-form dependencies:** `bump` moves a requirement written
  as `name = "req"` or `name = { version = "req", ... }` in the root
  `Cargo.toml`'s dependency tables; a renamed (`package = ...`) or
  `[dependencies.name]` form, or one in a member manifest, is left to Cargo,
  which then refuses the update.
- **Connected copy's own config:** `bump` runs from the connected copy, so a
  `.cargo/config.toml` or `rust-toolchain.toml` of the library itself applies
  to that one `cargo update`.

## `composition` relationship

Cargo has a single native mechanism for local-source override. Both
`dependency` connections are wired by a `[patch]` path. A `composition`
connection stays the project's own: Vibe64's adapter treats only
`dependency` connections.
