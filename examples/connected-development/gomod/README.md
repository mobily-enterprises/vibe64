# Connected development: Go modules (`gomod`)

This fixture proves that a Go project can build against an unpublished change
in a connected library checkout, using Go's own workspace mechanism, without
editing its tracked `go.mod` or `go.sum`.

## The recipe

1. The consumer (`app/`) requires the library by its ordinary module path and
   version: `require example.com/library v1.0.0`. Its `go.sum` holds the
   checksum of the published v1.0.0. Neither file changes during development.
2. Vibe64 writes the sources map to `.development/connected.json`.
3. **Prepare** (`go run ./tooling/connected prepare .development/connected.json`)
   reads the map with `encoding/json`. Each `gomod` entry's `sourceRoot` must be a
   Go module, and the script reads its module path from its `go.mod`. The script
   then writes an untracked `go.work` at the consumer root:

   ```
   // Generated by tooling/connected prepare. Untracked; do not commit.
   go 1.22
   use (
   	.
   	"/abs/path/to/library/checkout" // example.com/library (dependency)
   )
   ```

   The `go` line is the highest `go` version among the modules. Prepare is
   idempotent. It refuses to replace a `go.work` that it did not generate, and
   it refuses to run if `GOWORK` points somewhere else. If no `gomod` repository
   is connected, it removes its `go.work`.
4. **Verify** (`go run ./tooling/connected verify .development/connected.json`)
   proves that the connection is in effect. It does not simply exit with zero:
   - It checks that `go env GOWORK` names this `go.work`.
   - It runs `go list -deps ./...` over the consumer's own packages. At least
     one package of each connected module must appear. Each such package's
     `Module.Dir` and package `Dir` must be inside the connected `sourceRoot`.
   - It runs `go build ./...` and checks that the bytes of `go.mod` and `go.sum`
     are unchanged.
5. After Prepare, ordinary `go build`, `go run` and `go test` commands run from
   inside the consumer use the connected checkout. Go finds `go.work` in the
   current directory or a parent directory.

`.gitignore` excludes `/go.work`, `/go.work.sum` and `/.development/`.

## Why tracked manifests stay untouched

In workspace mode, every `use`d module is a main module. Go resolves
`example.com/library` straight from the connected directory. It needs no
version, download or checksum for it, so `go build` has nothing to write into
`go.mod` or `go.sum`. Any checksums the workspace does need for other modules
go into `go.work.sum`, which is also ignored. The Go reference says: "The go
command will maintain a `go.work.sum` file that keeps track of hashes used by
the workspace that are not in collective workspace modules' go.sum files". It
also advises against committing `go.work`. The proof checks this with
`git status --porcelain --untracked-files=all` (it must be empty) and
`git diff HEAD -- go.mod go.sum`.

Do not run `go work sync` or `go mod tidy` while connected. They write to the
modules' `go.mod` files, or work on a single module.

## Running the proof

```
PATH=/path/with/go:$PATH TMPDIR=/some/scratch bash prove.sh
```

Requirements: `go` (Go 1.22 or newer; tested with go1.25.0 linux/amd64), `git`
(tested with 2.43.0) and `zip` on `PATH`. The script sets `GOTOOLCHAIN=local`,
`GOSUMDB=off`, a private `GOMODCACHE`/`GOPATH` inside its temporary directory
and `GOPROXY=off`. If `GOCACHE` is set it is reused; otherwise a private one is
used. No network is needed.

What `prove.sh` does:

1. It "publishes" `library/` as `example.com/library v1.0.0` to a `file://`
   GOPROXY, as `.info`, `.mod`, `.zip` and `list` files.
2. It copies `app/` and runs `go mod tidy` against that proxy, which writes a
   real `go.sum` entry. It checks that the app prints `library 1.0.0 published`,
   then runs `git init` and commits the app.
3. It sets `GOPROXY=off` and runs `go clean -modcache`. It checks that a build
   now fails, so the published module cannot quietly supply the dependency.
4. It copies the library and changes its marker. This change is unpublished.
   It writes the sources map, runs Prepare twice (the resulting `go.work` must
   be identical) and runs Verify. It checks that `go run .` prints
   `library 1.0.0 + unpublished connected change`.
5. It checks that the checkout is clean and that `go.mod` and `go.sum` are
   unchanged.
6. Negative check: with `go.work` removed, Verify must fail.
7. It removes everything, letting `go clean -modcache` handle the read-only
   module cache.

## Limitations

- `-mod=mod` is rejected in workspace mode: "-mod may only be set to readonly or
  vendor when in workspace mode". Do not export `GOFLAGS=-mod=mod` while
  connected. A `vendor/` directory in the consumer does not combine with this
  recipe unless you use `go work vendor`, which this fixture does not cover.
- If `GOWORK=off`, or `GOWORK` points to a different file, the connection is
  bypassed. Verify detects this.
- If a connected `sourceRoot` disappears, every `go` command in the workspace
  fails, including `go run ./tooling/connected`. Run Prepare again with a
  current map, or delete `go.work`.
- A connected repository must be a single module at `sourceRoot`.
  Multi-module repositories need one entry per module.
- The connected module replaces the required version entirely. Its own
  requirements join the build list through minimal version selection. This
  can raise the versions of shared dependencies; that is the normal
  workspace behaviour.

## `composition` relationship

Go has only one native mechanism for consuming a module from local source.
Both `dependency` and `composition` entries are therefore wired the same way,
by `use` in `go.work`. The relationship is written into the `go.work` comment
and the output. Whatever `composition` means at the Genesis/Vibe64 level (how
the projects are combined) is handled outside the Go build. Verify still
requires every connected module to be part of the consumer's build.

```
== tools
go version go1.25.0 linux/amd64
== consumer checkout: resolve the published dependency, commit go.mod and go.sum
baseline output: library 1.0.0 published
== go offline and forget the published module
without the connection the build cannot obtain example.com/library (expected)
== prepare (first)
connected prepare: example.com/library -> /…/connected-gomod.XXXX/library (dependency)
== prepare (second, must be idempotent)
== verify
connected verify: example.com/library: 1 package(s) built from /…/connected-gomod.XXXX/library
connected verify: go build ./... succeeded in workspace mode; go.mod and go.sum unchanged
== run the consumer
output: library 1.0.0 + unpublished connected change
== tracked files untouched
git status --porcelain --untracked-files=all: clean (go.work, go.work.sum, .development/ are ignored)
== verify must fail without the connection

```
