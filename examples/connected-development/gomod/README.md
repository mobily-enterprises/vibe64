# Connected development: Go modules (`gomod`)

This fixture proves Vibe64's own `gomod` treatment: a Go project builds against
an unpublished change in a connected library checkout, through Go's own
workspace mechanism, without editing its tracked `go.mod` or `go.sum`; and on
Save those move to the checkout's new version tag only once the module proxy
has it.

## The recipe

`app/genesis/stack.md` declares only the default package type:

```
## Connected development

- Default package type: `gomod`
```

The project declares no Prepare or Verify command. For every `gomod`
`dependency` connection, workspace preparation runs Vibe64's adapter
(`packages/vibe64-project/src/server/connectedAdapters/gomod.js`):

1. The consumer (`app/`) requires the library by its ordinary module path and
   version: `require example.com/library v1.0.0`. Its `go.sum` holds the
   checksum of the published v1.0.0.
2. **Apply** writes an untracked `go.work` at the session source's module root,
   covering every connected Go module:

   ```
   // Generated by Vibe64 for this session's connected Go modules. Untracked; do not commit.

   go 1.22

   use (
   	.
   	"/abs/path/to/library/checkout" // example.com/library
   )
   ```

   The `go` line is the highest `go` version among the modules. Apply is
   idempotent. It refuses to replace a `go.work` it did not write, and refuses
   a tracked `go.work` or `go.work.sum`. Vibe64 keeps both out of Git through
   its own block in `.git/info/exclude`; the project's `.gitignore` need not
   name them.
3. **Proof** checks that `go.work` is the one apply would write now, that
   `go env GOWORK` names it, and that `go list -deps ./...` builds every package
   of the connected module from inside its checkout (`Module.Dir` and the
   package `Dir`). Session status runs the file check alone.
4. After apply, ordinary `go build`, `go run` and `go test` commands use the
   connected checkout. Go reads it in place, so a saved edit is in the next
   build; no watcher is needed.
5. **Save** (`bump`): Staging and Production build without the workspace,
   from the tracked `go.mod` and `go.sum`. `locked` reports the version
   `go.mod` requires. When the checkout's latest `v*` tag
   (`git describe --tags --abbrev=0 --match "v*"`) is newer than that,
   `GOWORK=off go get <module>@<tag>` moves `go.mod` and `go.sum` to it; Go
   fails for a version the proxy (or the repository) does not have, and then
   nothing changes and the line says why. An untagged commit, an older tag or
   an unreachable proxy never moves them.
6. When no Go module is connected any more, Vibe64 removes its `go.work` and
   Go's `go.work.sum`.

## Why tracked manifests stay untouched

In workspace mode, every `use`d module is a main module. Go resolves
`example.com/library` straight from the connected directory. It needs no
version, download or checksum for it, so `go build` has nothing to write into
`go.mod` or `go.sum`. Any checksums the workspace does need for other modules
go into `go.work.sum`. The Go reference says: "The go command will maintain a
`go.work.sum` file that keeps track of hashes used by the workspace that are
not in collective workspace modules' go.sum files". It also advises against
committing `go.work`. The proof checks this with
`git status --porcelain --untracked-files=all` (it must be empty) and
`git diff HEAD -- go.mod go.sum`. Only Save's bump changes them, on purpose.

Do not run `go work sync` or `go mod tidy` while connected. They write to the
modules' `go.mod` files, or work on a single module.

## Running the proof

```
PATH=/path/with/go:$PATH TMPDIR=/some/scratch bash prove.sh
```

Requirements: `go` (Go 1.22 or newer), `git`, `zip` and `node`, with this
repository's packages installed (the proof runs the adapter from
`packages/vibe64-project`). The script sets `GOTOOLCHAIN=local`,
`GOSUMDB=off`, a private `GOMODCACHE`/`GOPATH` inside its temporary directory
and `GOPROXY=off` (a `file://` proxy for the Save steps). If `GOCACHE` is set
it is reused; otherwise a private one is used. No network is needed.

What `prove.sh` does:

1. It "publishes" `library/` as `example.com/library v1.0.0` to a `file://`
   GOPROXY, as `.info`, `.mod`, `.zip` and `list` files.
2. It copies `app/` and runs `go mod tidy` against that proxy, which writes a
   real `go.sum` entry. It checks that the app prints `library 1.0.0 published`,
   then commits the app.
3. It sets `GOPROXY=off` and runs `go clean -modcache`. It checks that a build
   now fails, so the published module cannot quietly supply the dependency.
4. It copies the library as a Git checkout tagged `v1.0.0` and changes its
   marker without committing. It writes the sources map, runs the adapter's
   apply twice (the resulting `go.work` must be identical) and its proof, and
   checks that `go run .` prints `library 1.0.0 + unpublished connected change`.
5. It checks that the checkout is clean and that `go.mod` and `go.sum` are
   unchanged.
6. Negative check: with `go.work` moved away, the proof must fail.
7. Save: it commits `library 1.1.0 published` in the checkout and tags it
   `v1.1.0`. Bump reports `v1.1.0 is not published` and changes nothing. After
   publishing v1.1.0 to the proxy, bump moves `go.mod` and `go.sum` to it
   (and nothing else), the proof still passes, the connected build prints the
   checkout's newer working change, and `GOWORK=off` (Staging's view) prints
   the published `library 1.1.0 published`. A second bump changes nothing.
8. Disconnect: Vibe64's restore removes `go.work`; the consumer builds the
   published v1.1.0.
9. It removes everything, letting `go clean -modcache` handle the read-only
   module cache.

## Limitations

- The session source must have its `go.mod` at its root.
- `-mod=mod` is rejected in workspace mode: "-mod may only be set to readonly or
  vendor when in workspace mode". Do not export `GOFLAGS=-mod=mod` while
  connected. A `vendor/` directory in the consumer does not combine with this
  recipe unless you use `go work vendor`, which this fixture does not cover.
- If `GOWORK=off`, or `GOWORK` points to a different file, the connection is
  bypassed. The proof detects this.
- A connected repository must be a single module at its root.
- The connected module replaces the required version entirely. Its own
  requirements join the build list through minimal version selection. This
  can raise the versions of shared dependencies; that is the normal
  workspace behaviour.
- Bump moves only forward, to the latest tag reachable from the checkout's
  `HEAD`; a module with a major-version suffix (`/v2`) needs its tags to match.

## Evidence

Run `cad-godotnet-r2` on usone (Linux x86_64), offline apart from fetching the
toolchain from nixpkgs: go1.27.3 linux/amd64, git 2.53.0, Node v26.5.0, zip
from the host. The proof took 2 s with a warm `GOCACHE`. Excerpt:
