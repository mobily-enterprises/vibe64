# Connected development: Gradle (`gradle`)

Proves Vibe64's own `gradle` treatment with real Gradle: a Gradle consumer builds against a
connected library checkout through a native composite build in every ordinary Gradle command of
the session, with no flag and without any tracked file changing. On Save, a version the build's
repositories publish moves into the build script.

```
library/                 com.example:library:1.0.0 (Kotlin DSL, java-library + maven-publish)
app/                     application depending on com.example:library:1.0.0 (repositories: mavenLocal())
app/genesis/stack.md     the "## Connected development" section: only its default package type
app/.gitignore           /build/, /.gradle/, /.kotlin/
prove.sh                 end-to-end proof
```

## Recipe

```
## Connected development

- Default package type: `gradle`
```

Vibe64 needs nothing else. Its adapter
(`packages/vibe64-project/src/server/connectedAdapters/gradle.js`) runs in the `java` runtime,
which provides `java` and `gradle`, and in `git`. `prove.sh` drives it through
`examples/connected-development/vibe64-adapter.mjs` (`apply`, `proof`, `locked`, and Save's
`bump`), the way workspace preparation, session status and Save do.

**The session's own Gradle user home.** Gradle runs every script in its user home's `init.d` by
itself. So the session gets its own home, `.development/gradle-home`, and Vibe64 gives every
command of the session that home as `GRADLE_USER_HOME`: Preview, tests, the AI's commands and
workspace steps (`packages/vibe64-execution/src/server/env/connectedGradleEnv.js`, used by the
command environment for any command whose folder is in a tree holding Vibe64's script). A
command that names its own `GRADLE_USER_HOME` keeps it. Staging and Production build elsewhere,
with their own Gradle home, so they always build the published module.

**Apply** (after every Prepare step) runs no Gradle. It checks that the session source and each
checkout are Gradle builds that do not overlap, refuses an init script Vibe64 did not write, and
refuses a session that tracks anything in `.development/gradle-home`. It then writes
`.development/gradle-home/init.d/vibe64-connected.init.gradle.kts`, which covers every `gradle`
connection in Sources-file order:

```kotlin
// Generated by Vibe64 for connected development. Do not commit.
// Gradle reads it from the session's own Gradle user home, which Vibe64 gives every command of the session.
settingsEvaluated {
    // Library
    includeBuild("/abs/path/to/library/checkout")
}
```

- The person's own settings still apply: the session home links the default home's
  `gradle.properties` and each of its `init.d` scripts. The default home is what
  `GRADLE_USER_HOME` (else `~/.gradle`) names for a command outside the session.
- The shared read-only dependency cache (`GRADLE_RO_DEP_CACHE`): when none is published, or the
  published one is a day old, apply copies the default home's `caches/modules-2` into a new
  generation, without its `*.lock` and `gc.properties` files, as Gradle requires. Only a complete
  generation is published: `current` then names it. It is never written again. A command gets the
  generation `current` names when it starts and keeps it for its whole run, and a generation goes
  after a week, so no build is still reading it. Its root is the host's shared cache
  (`gradle-ro-dep-cache`), else the server login's `~/.cache/vibe64/gradle-ro-dep-cache`. A
  dependency it holds is never downloaded again by a session; one it lacks goes into the
  session's own home.
- Apply also writes the scripts that the proof and the published check use, beside the home in
  `.development/`. The home and the scripts are kept out of Git in the session's
  `connected gradle packages` exclude block, so nothing Gradle writes in the home reaches a commit.

**Proof** (after every Verify step, and in session status):

- Session status checks only that the init script is exactly what the session's connections
  produce.
- Preparation also requires that neither the home nor the scripts is tracked. It then runs
  `gradle -q --console=plain --no-daemon --no-configuration-cache -I <proof script> connectedProof`
  with the environment every command of the session gets, so with no connection flag.
  That task depends on `runtimeClasspath`, so Gradle builds the included checkout from source,
  and it prints each runtime artifact with the build it comes from. The proof requires one
  artifact from an included build whose file lies inside the checkout.

Gradle compiles the included build at each run, so a saved edit needs no new preparation, and the
adapter has no watch.

**Restore**: once no `gradle` connection remains, the session's Gradle home and the scripts go, so
the session's commands no longer get that home.

**Locked and bump (Save)**:

- `locked` reads two versions. The first is the root project's `group:name` and version that the
  checkout's build declares (`group`/`version` in the build script or `gradle.properties`, and
  `rootProject.name`). The second is the version the session build names in string notation in
  its build scripts, or in `gradle.lockfile` when it locks; Staging and Production resolve that
  one. A version catalog reads as unknown.
- `bump` moves each string notation to the checkout's version only when Gradle resolves that
  module from the build's own repositories.
  - The check runs a detached configuration through a separate init script in the default
    Gradle home, whose `init.d` has no connection, never the composite.
  - It then rewrites `gradle.lockfile` with `gradle dependencies --write-locks` in that home when
    the build locks. If that fails, the script edit is undone.
  - A `-SNAPSHOT` is never looked up. An unpublished version, or an unreachable repository,
    changes nothing and leaves a line saying why.

## Why tracked files stay untouched

The tracked `settings.gradle.kts` and `build.gradle.kts` are never edited by apply, and the
dependency stays `com.example:library:1.0.0`. All derived state is in the Git-excluded
`.development/` (the session's Gradle home included) and the ignored `build/` and `.gradle/`. Composite substitution installs nothing.
The proof checks that the "published" 1.0.0 jar is unchanged. Only `bump` edits the build script,
on Save, and only to a published version.

## Limitations

- A command gets the session's Gradle home when it starts. A terminal opened before preparation
  put the connection in effect keeps its environment: open a new one. A command that still names
  the home after the connection is removed (an AI agent started while it was connected carries it)
  no longer gets it, so Gradle never makes the home again outside the Git exclude.
- A dependency only connected sessions download reaches the shared cache only through the
  default home: until then, each session downloads it once into its own home.
- The shared cache is copied from the default home while Gradle there may be writing; the copy
  leaves out its locks, as Gradle says, but a file written during the copy may be incomplete.
- Substitution matches `group:name`. If the checkout's coordinates differ from the dependency,
  nothing is substituted and the proof says so.
- Only the checkout's root project is read for `locked` and `bump`.
- The consumer's Gradle builds the included build, so the two must be compatible.
- Vibe64 runs `gradle` from the runtime, never `./gradlew`.
- A full JDK is required.
- The published check trusts the build's repositories. A build that reads `mavenLocal()`, as this
  fixture does, treats what is installed there as published. The composite itself never installs
  anything there.

## Running the proof

```
PROOF_CACHE_DIR=<scratch>/cache/gradle ./prove.sh
```

The proof uses an isolated default `GRADLE_USER_HOME` (no daemon; `mavenLocal()` inside the cache)
and its own cache folder for the shared cache, and runs the session's Gradle `--offline`. It runs
the app as a session command does: with only the environment Vibe64 gives it. A module served by a
localhost Maven repository, downloaded once by the default home, is then read by a session command
offline from the shared read-only cache, and the session's home has no copy of it.

The Save step publishes a released 1.1.0 to that `mavenLocal()` and shows three things:

- The checkout's 1.1.0 moves `build.gradle.kts` to it, with exactly one changed line, while the
  session's commands still build the connected source. `locked` shows the published 1.0.0 before and
  1.1.0 after.
- A run in the default home (Staging's view) uses the released 1.1.0.
- The checkout's 1.2.0 does not move the build script, and Save's lines say Staging and
  Production keep 1.1.0 until 1.2.0 is published.

## Evidence

Run `cad-gh-r3` on usone (container `v64tests-1`, 2026-11-23) passed in 175 s, with Gradle
8.14.8, OpenJDK 21.0.13 (both from nixpkgs through `nix build`) and Node v26.5.0. The session's
commands ran the app with no flag, and read the localhost module offline from the shared
read-only cache. Its Save lines:

```
[Connected] Library: Staging and Production now use the published com.example:library 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0.
[Connected] Library: com.example:library 1.2.0 is not published; Staging and Production keep 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0 until 1.2.0 is published, which Save then moves this project to.
```

Between them, a run in the default home printed `APP USES LIBRARY-MARKER-RELEASED-1.1.0`.
