# Connected development: Gradle (`gradle`)

Proves Vibe64's own `gradle` treatment with real Gradle: a Gradle consumer builds against a
connected library checkout through a native composite build, without any tracked file
changing. On Save, a version the build's repositories publish moves into the build script.

```
library/                 com.example:library:1.0.0 (Kotlin DSL, java-library + maven-publish)
app/                     application depending on com.example:library:1.0.0 (repositories: mavenLocal())
app/genesis/stack.md     the "## Connected development" section: only its default package type
app/.gitignore           /build/, /.gradle/, /.kotlin/
prove.sh                 end-to-end proof
```

## Recipe

```
## Connected development

- Default package type: `gradle`
```

Vibe64 needs nothing else. Its adapter
(`packages/vibe64-project/src/server/connectedAdapters/gradle.js`) runs in the `java` runtime,
which provides `java` and `gradle`, and in `git`. `prove.sh` drives it through
`examples/connected-development/vibe64-adapter.mjs` (`apply`, `proof`, `locked`, and Save's
`bump`), the way workspace preparation, session status and Save do.

**Apply** (after every Prepare step) runs no Gradle. It checks that the session source and each
checkout are Gradle builds that do not overlap, and refuses an init script Vibe64 did not write.
It then writes the Git-excluded `.development/connected.init.gradle.kts`, which covers every
`gradle` connection in Sources-file order:

```kotlin
// Generated by Vibe64 for connected development. Do not commit.
// Use: gradle -I .development/connected.init.gradle.kts <tasks>
settingsEvaluated {
    // Library
    includeBuild("/abs/path/to/library/checkout")
}
```

Apply also writes the scripts that the proof and the published check use. All three are kept out
of Git in the session's `connected gradle packages` exclude block.

**Gradle applies an init script only to a command that passes it.** While the session is
connected, every Gradle command that should use the connected checkout passes
`-I .development/connected.init.gradle.kts`; apply's line says so. Gradle has no untracked,
project-local file it applies by itself. That is also why Staging and Production, which never
pass it, always build the published module.

**Proof** (after every Verify step, and in session status):

- Session status checks only that the init script is exactly what the session's connections
  produce.
- Preparation also requires that none of the scripts is tracked. It then runs
  `gradle -q --console=plain --no-daemon --no-configuration-cache -I <init> -I <proof script> connectedProof`.
  That task depends on `runtimeClasspath`, so Gradle builds the included checkout from source,
  and it prints each runtime artifact with the build it comes from. The proof requires one
  artifact from an included build whose file lies inside the checkout.

Gradle compiles the included build at each run, so a saved edit needs no new preparation, and the
adapter has no watch.

**Restore**: once no `gradle` connection remains, the scripts go.

**Locked and bump (Save)**:

- `locked` reads two versions. The first is the root project's `group:name` and version that the
  checkout's build declares (`group`/`version` in the build script or `gradle.properties`, and
  `rootProject.name`). The second is the version the session build names in string notation in
  its build scripts, or in `gradle.lockfile` when it locks; Staging and Production resolve that
  one. A version catalog reads as unknown.
- `bump` moves each string notation to the checkout's version only when Gradle resolves that
  module from the build's own repositories.
  - The check runs a detached configuration through a separate init script, never the composite.
  - It then rewrites `gradle.lockfile` with `gradle dependencies --write-locks` when the build
    locks. If that fails, the script edit is undone.
  - A `-SNAPSHOT` is never looked up. An unpublished version, or an unreachable repository,
    changes nothing and leaves a line saying why.

## Why tracked files stay untouched

The tracked `settings.gradle.kts` and `build.gradle.kts` are never edited by apply, and the
dependency stays `com.example:library:1.0.0`. All derived state is in the Git-excluded
`.development/` and the ignored `build/` and `.gradle/`. Composite substitution installs nothing.
The proof checks that the "published" 1.0.0 jar is unchanged. Only `bump` edits the build script,
on Save, and only to a published version.

## Limitations

- Gradle needs `-I .development/connected.init.gradle.kts` on every connected run.
- Substitution matches `group:name`. If the checkout's coordinates differ from the dependency,
  nothing is substituted and the proof says so.
- Only the checkout's root project is read for `locked` and `bump`.
- The consumer's Gradle builds the included build, so the two must be compatible.
- Vibe64 runs `gradle` from the runtime, never `./gradlew`.
- A full JDK is required.
- The published check trusts the build's repositories. A build that reads `mavenLocal()`, as this
  fixture does, treats what is installed there as published. The composite itself never installs
  anything there.

## Running the proof

```
PROOF_CACHE_DIR=<scratch>/cache/gradle ./prove.sh
```

The proof uses an isolated `GRADLE_USER_HOME` (no daemon; `mavenLocal()` inside the cache), runs
Gradle `--offline`, and downloads nothing.

The Save step publishes a released 1.1.0 to that `mavenLocal()` and shows three things:

- The checkout's 1.1.0 moves `build.gradle.kts` to it, with exactly one changed line, while the
  init script still builds the connected source. `locked` shows the published 1.0.0 before and
  1.1.0 after.
- A run without the script uses the released 1.1.0.
- The checkout's 1.2.0 does not move the build script, and Save's lines say Staging and
  Production keep 1.1.0 until 1.2.0 is published.

## Evidence

Run `cad-jvm-p3` on usone (container `v64tests-1`, 2026-11-23) passed in 118 s, with Gradle
8.14.8, OpenJDK 21.0.13 (both from nixpkgs through `nix shell`) and Node v26.5.0, offline. Its
Save lines:

```
[Connected] Library: Staging and Production now use the published com.example:library 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0.
[Connected] Library: com.example:library 1.2.0 is not published; Staging and Production keep 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0 until 1.2.0 is published, which Save then moves this project to.
```

Between them, a run without the init script printed `APP USES LIBRARY-MARKER-RELEASED-1.1.0`.
