# Connected development: Gradle (`gradle`)

This acceptance fixture proves that a Gradle consumer can build against a connected library
checkout through a native **composite build** without modifying any tracked file.

```
library/                 com.example:library:1.0.0 (Kotlin DSL, java-library + maven-publish)
app/                     application depending on com.example:library:1.0.0 (repositories: mavenLocal())
app/tooling/Connected.java   Prepare/Verify (Java 11+ single-file source program)
app/genesis/stack.md     the "## Connected development" section only
app/.gitignore           /build/, /.gradle/, /.kotlin/, /.development/
prove.sh                 end-to-end proof
```

The sources are Java with Kotlin DSL build scripts. A Kotlin-source consumer would use
`kotlin` as the runtime id and works the same way, because the substitution is
language-independent.

## Recipe

```
## Connected development

- Default package type: `gradle`
- Sources file: `.development/connected.json`
- Prepare `Use connected Gradle builds` with `java`: `java` `tooling/Connected.java` `prepare` `.development/connected.json`
- Verify `Prove connected Gradle builds` with `java`: `java` `tooling/Connected.java` `verify` `.development/connected.json`
```

`java` is the Vibe64 runtime id; that runtime provides `java`, `mvn` and `gradle`. For a Kotlin
build use `kotlin`.

**Prepare** (run from the consumer checkout root) works in three steps:

1. It reads and validates the sources map with a small, strict RFC 8259 parser, because Java
   has no standard JSON API. Entries without `type` use the stack default `gradle`. Entries of
   another type are skipped, and a map with no `gradle` entry is an error.
2. It writes the git-ignored init script `.development/connected.init.gradle.kts`:
   ```kotlin
   // Generated by tooling/Connected.java for Vibe64 connected development. Do not commit.
   // Use: gradle -I .development/connected.init.gradle.kts <tasks>
   settingsEvaluated {
       // Library (dependency)
       includeBuild("/abs/path/to/library/checkout")
   }
   ```
   Prepare refuses to overwrite a tracked init script, or one it did not write. If the path is
   not already ignored, Prepare appends it to `.git/info/exclude`.
3. Prepare does not run Gradle. Running Prepare twice produces a byte-identical file, and the
   proof checks this.

The consumer then runs its ordinary tasks with the init script, for example
`gradle -I .development/connected.init.gradle.kts run`. This is equivalent to passing
`--include-build <sourceRoot>` for each connected checkout. The project's `./gradlew` works
the same way.

**Verify** proves the substitution in four steps:

1. It checks that the init script exists, is untracked, and exactly matches what the current
   sources map produces.
2. It runs Gradle with that init script plus a throw-away proof init script, which registers
   `connectedProof` on every `java` project. The command is
   `gradle -q --no-configuration-cache -I <init> -I <proof> connectedProof`, plus any arguments
   in `CONNECTED_GRADLE_ARGS`.
3. `connectedProof` depends on `runtimeClasspath`, so Gradle builds the included build from
   source. It then prints every resolved artifact with its component id and its
   `ProjectComponentIdentifier.build.buildPath`.
4. For each connected project, Verify requires a runtime artifact that comes from an included
   build (build path other than `:`) and whose file lies inside that checkout. Example:
   `com.example:library:1.0.0 -> project ':library'` resolves to
   `<sourceRoot>/build/libs/library-1.0.0.jar`.

## Native mechanism used

Gradle composite builds (https://docs.gradle.org/9.8.1/userguide/composite_builds.html):

- `Settings.includeBuild(path)` turns the build into a composite.
- Gradle automatically substitutes an external module `group:name` with the included build's
  project of the same coordinates.
- The CLI equivalent is `--include-build`.

The fixture calls `includeBuild` from an init script's `settingsEvaluated {}` hook. That is the
standard `Gradle.settingsEvaluated(Action<Settings>)` API, which keeps the project's tracked
`settings.gradle.kts` untouched. Gradle compiles the included build on demand, so edits to
connected source take effect on the next build without running Prepare again. The proof
demonstrates this.

## Why tracked files stay untouched

The tracked `settings.gradle.kts` and `build.gradle.kts` are never edited, the dependency stays
`com.example:library:1.0.0`, and there is no lockfile. All derived state lives in the
git-ignored `.development/`, `build/` and `.gradle/`.

`prove.sh` asserts that `git status --porcelain --untracked-files=all` is empty and that the
index is unchanged. It also asserts that the "published" 1.0.0 jar in the Maven repository is
unchanged. Composite substitution never publishes or installs anything.

## `composition` relationship

The relationship is recorded in the generated script comment, but both relationships use the
same wiring: the included build replaces the module the consumer depends on.

## Limitations

- **Gradle needs the init script on every run.** Gradle has no untracked, project-local file
  that it applies automatically. The project's launch commands must pass
  `-I .development/connected.init.gradle.kts` (or `--include-build`) while connected. The
  alternatives are user-global init scripts (`$GRADLE_USER_HOME/init.d`), which are not
  project-scoped, or a one-time tracked opt-in in `settings.gradle.kts` that reads an untracked
  file.
- **Version and coordinates.** Substitution matches `group:name`, where `name` is the included
  project's name; the version is ignored. If the checkout's coordinates differ from the
  consumer's dependency, nothing is substituted and Verify fails. The proof exercises this case
  by renaming `rootProject.name`.
- **Gradle version.** The consumer's Gradle version builds the included build, which must be
  compatible with it.
- **Full JDK required.** Gradle refuses a JRE-only Java (`does not provide the required
  capabilities: [JAVA_COMPILER]`). The host's Ubuntu `openjdk-21-jre` is JRE-only, so the proof
  used Temurin 21.
- **Configuration cache.** Verify disables the configuration cache for its proof task only.
- **Absolute paths.** The init script holds absolute paths. Run Prepare again if the connected
  checkouts move.

## Running the proof

```
export JAVA_HOME=<full JDK 17+>   # proof used Temurin 21.0.12.1+1
export PATH="$JAVA_HOME/bin:<gradle-9.8.1>/bin:$PATH"
PROOF_CACHE_DIR=<scratch>/cache/gradle ./prove.sh
```

`prove.sh` runs with an isolated `GRADLE_USER_HOME` under `PROOF_CACHE_DIR`. That directory has
a `gradle.properties` setting `org.gradle.daemon=false`, so no daemon is left running, and
`systemProp.maven.repo.local=<cache>/m2`, so `mavenLocal()` is isolated. The proof runs
`--offline` throughout and downloads nothing.

The proof steps are:

1. Publish the original library as the "published" 1.0.0.
2. Copy both projects into a fresh `mktemp` directory, then `git init` and commit the app.
3. Run the baseline, which prints the original marker.
4. Modify the library and write the sources map.
5. Run Prepare twice and check the output is idempotent, then run Verify.
6. Run the app with the init script and check it prints the modified marker.
7. Edit the library again, then run Verify and the app again; the new marker appears without
   another Prepare.
8. Run the negative checks: removing the wiring and renaming the module must each make Verify
   fail.
9. Check that `git status` is clean, then clean up.

Tools: Gradle 9.8.1 (SHA-256 verified; embedded Kotlin 2.4.10) and Temurin OpenJDK 21.0.12.1+1
(SHA-256 verified).
