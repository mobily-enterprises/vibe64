# Connected development: Maven (`maven`)

Proves Vibe64's own `maven` treatment with real Maven: a Maven consumer builds against a
connected library checkout without any tracked file changing, and on Save a version the remote
repositories publish moves into `pom.xml`.

```
library/                 com.example:library:1.0.0, Library.marker() returns a marker string
app/                     com.example:app, depends on com.example:library:1.0.0
app/genesis/stack.md     the "## Connected development" section: only its default package type
app/.gitignore           /target/
prove.sh                 end-to-end proof
```

## Recipe

```
## Connected development

- Default package type: `maven`
```

Vibe64 needs nothing else. Its adapter
(`packages/vibe64-project/src/server/connectedAdapters/maven.js`) runs in the `java` runtime,
which provides `java` and `mvn`, and in `git`. `prove.sh` drives it through
`examples/connected-development/vibe64-adapter.mjs` (`apply`, `proof`, `locked`, and Save's
`bump`), the way workspace preparation, session status and Save do.

**Apply** (after every Prepare step) does this:

1. It checks the session source and each checkout have a `pom.xml` and do not overlap. It also
   checks that Maven is 3.9.3 or later.
2. It asks Java for the `user.home` Maven uses. The developer's repository
   `<user.home>/.m2/repository` becomes the read-only tail.
3. It refuses a tracked `.mvn/maven.config`, or one that Vibe64 did not write.
4. It installs every connected checkout of the type, in Sources-file order, into
   `.development/maven-connected-repository`:
   `mvn -B -q -f <checkout>/pom.xml -Dmaven.repo.local=<that repository> -Dmaven.repo.local.tail=<tail> -DskipTests install`.
   It first removes the version folders of its earlier installs, so a version the checkout no
   longer builds, or a connection that went, cannot shadow a published one. Plugins Maven
   downloaded there stay.
5. It writes `.mvn/maven.config`, which selects the pair for every ordinary `mvn`:
   ```
   # Generated by Vibe64 for connected development. Do not commit.
   -Dmaven.repo.local=<session>/.development/maven-connected-repository
   -Dmaven.repo.local.tail=<user.home>/.m2/repository
   ```
   It also writes `.development/maven-connected.json`, which records each checkout's build
   inputs (every `pom.xml` and every file under `src/`) and the installed jars.
6. It keeps these out of Git in the session's own `.git/info/exclude` block,
   `connected maven packages`: both files, the repository, the proof's classpath file and the
   published check's repository.

An apply over an unchanged checkout runs no install.

**Watch**: while the session runs, the shared watcher watches each connected checkout and applies
the connection again after a save. The install writes the checkout's `target/`, which wakes the
watcher once more; that apply finds the build inputs unchanged and installs nothing.

**Proof** (after every Verify step, and in session status) checks these in order:

1. The config selects the connected repository.
2. The record names this checkout.
3. No build input changed since the install. A Maven install is a snapshot, so after an edit
   the proof says which file changed, and preparing again (or the session's watcher after a
   save) installs it again.
4. The installed jars are the ones built.

Session status stops there. Preparation also does these checks:

1. It requires that none of those paths is tracked.
2. It asks Maven, through the ordinary command path (so `.mvn/maven.config` applies), for the
   runtime classpath:
   `mvn -B -q org.apache.maven.plugins:maven-dependency-plugin:3.11.0:build-classpath -Dmdep.outputFile=… -Dmdep.includeScope=runtime`.
3. It requires a classpath entry inside the connected repository that is byte-identical to a jar
   the install recorded. When `pom.xml` asks for a version the checkout does not build, Maven
   resolves the published one, and the proof says so.

**Restore**: once no `maven` connection remains, the derived files and the connected repository
go. A project's own `.mvn/maven.config` is never touched.

**Locked and bump (Save)**:

- `locked` reads two versions for every artifact of the checkout (its pom and its modules') that
  the session's `pom.xml` names. The first is what the checkout's pom declares. The second is
  what the tracked `pom.xml` names, as a literal or as a property of the same pom; Staging and
  Production resolve this one. A version from a parent or a BOM reads as unknown.
- `bump` moves `pom.xml` to the checkout's version only when Maven finds that version in the
  project's remote repositories.
  - The check resolves `g:a:V:pom` with `-U` into `.development/maven-published-repository`, a
    repository that only remote repositories ever fill. On the command line,
    `-Dmaven.repo.local` and `-Dmaven.repo.local.tail` both name that repository, and the command
    line wins over `.mvn/maven.config`. So neither the connected install nor the developer's
    repository can answer.
  - A `-SNAPSHOT` is never looked up. An unpublished version, or an unreachable repository,
    changes nothing and leaves a line saying why.
  - The edit is the one dependency `<version>` (or the one property) that names it, and nothing
    else.

## Why tracked files stay untouched

`pom.xml` keeps `com.example:library:1.0.0`. The connected build goes into a project-local,
Git-excluded repository under the same coordinates, and the Git-excluded `.mvn/maven.config`
selects it. The developer's repository (the tail) is only read, and the proof checks that the
"published" 1.0.0 in it is unchanged. Only `bump` edits `pom.xml`, on Save, and only to a
published version.

## Limitations

- Maven 3.9.3 or later, and a full JDK.
- The tail is Maven's default for `user.home`. A `<localRepository>` in `settings.xml` is not
  followed, so Maven downloads into the connected repository instead. That is slower, but just
  as correct.
- An install is a snapshot. Until the connection is applied again (preparation, or the watcher
  after a save), the proof reports the connection as stale.
- The checkouts install in Sources-file order. List a connected library before another one that
  depends on it.
- Only jars count. An install that puts only a pom (a BOM, a parent) is refused. A parent pom
  of a multi-module checkout stays in the connected repository until that repository is
  restored.
- A project that tracks `.mvn/maven.config` is refused.
- `mvn` comes from the runtime, never `./mvnw`.
- The proof needs `maven-dependency-plugin:3.11.0`, cached or downloadable.

## Running the proof

```
PROOF_CACHE_DIR=<scratch>/cache/maven ./prove.sh
```

`JAVA_TOOL_OPTIONS=-Duser.home=<cache>/home` makes the cache's `home/.m2/repository` the
developer's repository for both the adapter and Maven. The first run fills it online with the
"published" library 1.0.0 and the plugins. From then on everything runs with
`MAVEN_ARGS="-B -o"`.

The Save step serves a `file://` remote repository through a `settings.xml` mirror. That
repository is a copy of the cache plus a released library 1.1.0. The step shows two things:

- The checkout's 1.1.0 moves `pom.xml` to it, with exactly one changed line, while the app still
  runs the connected source. `locked` shows the published 1.0.0 before and 1.1.0 after, and
  Save's lines say Staging and Production now use the published 1.1.0.
- The checkout's 1.2.0 does not move `pom.xml`, although the connected install holds 1.2.0, and
  Save's lines say Staging and Production keep 1.1.0 until 1.2.0 is published.

## Evidence

Run `cad-jvm-p3` on usone (container `v64tests-1`, 2026-11-23) passed in 63 s, with Apache
Maven 3.10.1, OpenJDK 21.0.13 (both from nixpkgs through `nix shell`) and Node v26.5.0. An
earlier run (`cad-jvm-p2`) had filled the cache online; this one used no network, the Save
step's remote being the `file://` repository. Its Save lines:

```
[Connected] Library: Staging and Production now use the published com.example:library 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0.
[Connected] Library: com.example:library 1.2.0 is not published; Staging and Production keep 1.1.0.
[Connected] Library: this session runs the connected com.example:library; Staging and Production use the published 1.1.0 until 1.2.0 is published, which Save then moves this project to.
```
