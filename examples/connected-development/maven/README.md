# Connected development: Maven (`maven`)

Acceptance fixture proving that a Maven consumer can build against a connected library
checkout using only native Maven features, without modifying any tracked file.

```
library/                 com.example:library:1.0.0, Library.marker() returns a marker string
app/                     com.example:app, depends on com.example:library:1.0.0
app/tooling/Connected.java   Prepare/Verify (Java 11+ single-file source program)
app/genesis/stack.md     the "## Connected development" section only
app/.gitignore           /target/, /.development/, /.mvn/maven.config
prove.sh                 end-to-end proof
```

## Recipe

```
## Connected development

- Default package type: `maven`
- Sources file: `.development/connected.json`
- Prepare `Use connected Maven artifacts` with `java`: `java` `tooling/Connected.java` `prepare` `.development/connected.json`
- Verify `Prove connected Maven artifacts` with `java`: `java` `tooling/Connected.java` `verify` `.development/connected.json`
```

(`java` is the Vibe64 runtime id; that runtime provides `java`, `mvn` and `gradle`.)

**Prepare** (run from the consumer checkout root):

1. Reads and validates the sources map (strict, small RFC 8259 parser in the tool; Java has no
   standard JSON API). Entries without `type` use the stack default `maven`; entries of another
   type are skipped; a map with no `maven` entry is an error.
2. Deletes and recreates the project-local head repository
   `.development/maven-connected-repository`, so nothing stale or disconnected survives.
3. For each connected checkout runs, in that checkout:
   `mvn -B -q -f <sourceRoot>/pom.xml -Dmaven.repo.local=<app>/.development/maven-connected-repository -Dmaven.repo.local.tail=<tail> -DskipTests install`
   (`./mvnw` is used when the checkout has an executable wrapper.)
4. Writes the git-ignored `.mvn/maven.config`:
   ```
   # Generated by tooling/Connected.java for Vibe64 connected development. Do not commit.
   -Dmaven.repo.local=<app>/.development/maven-connected-repository
   -Dmaven.repo.local.tail=<tail>
   ```
   so every ordinary `mvn ...` in the consumer checkout resolves connected artifacts first.
   It refuses if `.mvn/maven.config` is tracked or was not written by the tool. If either
   derived path is not already ignored it appends it to `.git/info/exclude`.

`<tail>` is `CONNECTED_MAVEN_TAIL` or `~/.m2/repository`: the developer's ordinary cache, used
read-only for plugins and third-party dependencies.

**Verify**:

1. Checks `.mvn/maven.config` selects the head repository and is untracked.
2. Runs `mvn -B -q org.apache.maven.plugins:maven-dependency-plugin:3.11.0:build-classpath`
   in the consumer through the ordinary command path, so `.mvn/maven.config` applies, and reads
   the resolved runtime classpath.
3. For each connected project, requires a classpath entry inside the head repository that is
   byte-identical (SHA-256) to a jar under the checkout's `target/`.
4. Fails if `pom.xml` or anything under `src/` in the checkout is newer than that jar. A
   Maven install is a snapshot of the source, so after editing connected source you must run
   Prepare again.

## Native mechanisms used (Maven 3.9.3+)

- **Chained local repository**, `maven.repo.local.tail`, added in Maven 3.9.0 (release notes:
  "Chained local repository"). Maven reads the head first and then the tail, and writes only
  to the head. Present as `maven.repo.local.tail` in 3.9.16.
- **`.mvn/maven.config`** (https://maven.apache.org/configure.html): one argument per line
  since 3.9.0, and `#` comments since 3.9.3.
- `MAVEN_ARGS`: a Maven 3.9.0+ environment variable, which the proof uses for `-B -o`.

## Why tracked files stay untouched

`pom.xml` keeps `com.example:library:1.0.0`. The connected build is installed under the same
coordinates into a git-ignored, project-local repository, and is selected by the git-ignored
`.mvn/maven.config`. `prove.sh` asserts that `git status --porcelain --untracked-files=all` is
empty and that the index (`git ls-files -s`) is unchanged.

## Shadowing a release version (1.0.0)

The consumer requires the fixed version `1.0.0`, so the connected install must use that
version. Shadowing a release is safe here only because of where the shadowed copy lives:

- It goes only into the per-checkout head repository. The shared `~/.m2` (the tail) is never
  written. The proof checks that the "published" 1.0.0 jar in the tail is byte-for-byte
  unchanged, and that `~/.m2` was never created.
- Prepare rebuilds the head from scratch each time. Removing `.mvn/maven.config` (or the
  `.development/` directory) restores the published artifact.
- Release artifacts are never re-checked against remotes, so a shadow in a shared repository
  would persist silently. That is why the shadow must never go there.

A `-SNAPSHOT` version would avoid shadowing but needs a tracked pom change on both sides, and
the consumer pins a release. If the checkout builds a different version than the consumer
requests (for example `1.1.0-SNAPSHOT`), Maven resolves the published 1.0.0. Verify detects
this and fails; `prove.sh` exercises that case.

**Alternative considered: an aggregator reactor.** An untracked `.development/pom.xml`
listing the app and `<sourceRoot>` as `<modules>` gets reactor resolution from source, with no
install and no staleness. It was rejected for three reasons:

- Every developer and launch command would have to run `mvn -f .development/pom.xml ...`
  instead of the project's ordinary commands.
- Module paths must be relative.
- Reactor resolution also requires exactly matching versions.

The install-plus-chained-repository approach keeps ordinary `mvn` commands working.

## `composition` relationship

The relationship is recorded and printed but is wired the same way: the consumer depends on
the checkout's artifact, and the checkout's installed build replaces it.

## Limitations

- Requires Maven 3.9.3+ (checked by the tool) and a full JDK for `maven.compiler.release`.
  The host's Ubuntu `openjdk-21-jre` lacks `javac`/`ct.sym`, so the proof used Temurin 21.
- Connected checkouts are installed in sources-map order. If one connected library depends on
  another connected library, list the dependency first.
- Multi-module checkouts are installed whole. Verify matches any jar under a `target/`
  directory up to 6 levels deep.
- An absolute path is written into `.mvn/maven.config`, so run Prepare again if the checkout
  moves.
- A project that tracks `.mvn/maven.config` is refused. Such a project would put the two `-D`
  arguments in `MAVEN_ARGS` for its launch commands instead.
- If `~/.m2/settings.xml` sets `<localRepository>`, set `CONNECTED_MAVEN_TAIL` to that path.
- Verify needs `maven-dependency-plugin:3.11.0` to be resolvable (cached, or online).

## Running the proof

```
export JAVA_HOME=<full JDK 17+>   # proof used Temurin 21.0.12.1+1
export PATH="$JAVA_HOME/bin:<apache-maven-3.9.16>/bin:$PATH"
PROOF_CACHE_DIR=<scratch>/cache/maven ./prove.sh
```

On its first run `prove.sh` populates `PROOF_CACHE_DIR/repository` online. It installs the
original library as the "published" 1.0.0 and fetches the plugins. All later steps run with
`MAVEN_ARGS="-B -o"`, which keeps them offline.

The proof does the following:

1. Copies `library` and `app` into a fresh `mktemp` directory and commits the app with
   `git init`.
2. Runs a baseline, which prints the original marker.
3. Modifies the library marker and writes the sources map.
4. Runs Prepare twice, then Verify.
5. Runs `mvn -q compile exec:java` with no repository flags and asserts the modified marker.
6. Runs three negative checks; Verify must fail for each:
   - stale source;
   - `.mvn/maven.config` removed;
   - a version mismatch.
7. Asserts a clean `git status`, then cleans up.

Tools used: Apache Maven 3.9.16 (SHA-512 verified), Temurin OpenJDK 21.0.12.1+1 (SHA-256
verified), maven-dependency-plugin 3.11.0, exec-maven-plugin 3.6.4.
